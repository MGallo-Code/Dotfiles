# UI Style (always on)

Michael's settled UI rules for every interface an agent builds, mocks or reviews. Wording, labels and redundancy come first: they are the corrections he has made most. Full form with why and examples: the `ui-style` skill's `always.md`.

- **UI-01 Copy about content, not machinery.** Write copy about user content in the user's words, never code terms, function names, database IDs, file paths, pipeline stages, version tags or decision logic. Yes: Ships Tuesday. No: Ships Tuesday (SLA rule 4 applied).
- **UI-02 Action labels name the effect.** Label each action with the short verb or noun for what pressing it does, adding no count, qualifier, mechanism, list name, or consequence. Yes: Save, on a card that saves a recipe to favorites. No: Create, on that same card.
- **UI-03 Each fact shown once.** Show each fact once per screen: cut any title, count, chip, icon or status word repeating another element, and any chip that never changes value. Yes: A notifications switch shown on, with no "Enabled" word beside it. No: The same switch with the word "Enabled" beside it.
- **UI-04 Plain characters in copy.** Write copy with no em dashes, using a comma, colon or period instead, and no unrendered HTML entities such as &#39;. Yes: You're booked for Tue Sep 15: we'll email a reminder. No: You&#39;re booked for Tue Sep 15 — we&#39;ll email a reminder.
- **UI-05 One name per thing.** Give each concept, section and act one name everywhere, exactly as broad as what it covers; an act spanning item types uses each type's verb. Yes: "Completed" on the task row, its filter and its history. No: "Completed" on the row but "Done" in the filter.
- **UI-06 Instructions match the screen.** Name only controls present where the text is read, by their exact labels, and never contradict an example shown beside it. Yes: "Remove it from its page", where that page has a Remove button. No: "Click Archive" on a screen whose button reads File.
- **UI-07 Status shown in place.** Show status on the item or control it concerns, never a toast or floating pill; report a failure or skip in one line beside it. Yes: A shop's + on a product turns to ✓ once it is in the cart. No: A "Saved!" toast sliding up over the page.
- **UI-08 Statuses show only verified truth.** Derive every status, count, list and empty state from current data, not hard-coded or stale values, updated without reload; mark unconfirmed items; timestamp synced lists. Yes: Completing a task changes `4 due today` to `3 due today` at once. No: `Synced` on the dashboard while every save errors.
- **UI-09 Started flows open on the task.** Put no how-to text on task screens or their menus, and open a started flow on its first step; explain its scope before Start. Yes: An attach menu listing Photo, Voice, File. No: The same menu headed "Pick one".
- **UI-10 Sample data stays in mocks.** Fill mocks and dev builds with real-looking sample data, never stubs or coming-soon pages; ship a screen only once its live data is wired. Yes: A contacts mock showing five sample contacts in its real layout. No: A shipped page reading "Coming soon".
- **UI-11 Hairlines, not boxes.** Separate sections with a 1px line, never a box; run lists and banners full width, square-cornered, text on one left edge; cards only in grids. Yes: Account settings: 'Notifications' and 'Billing' split by one 1px rule, each name on the page title's 16px line. No: A bordered 'Billing' card inside a padded, bordered settings panel.
- **UI-12 One conventional meaning per glyph.** Give each action or state the simple outline glyph whose everyday meaning it is, filled only when on, and never reuse it for another meaning. Yes: A trash can on Clear. No: A broom on Clear.
- **UI-13 Shared components and style variables.** Render each repeated element through the app's one existing component, adding options for real differences, and take fonts, spacing and colors from global variables. Yes: A new Invoices page uses the existing page header, list row and bottom bar components unchanged. No: A new Invoices page with a hand-built header that mimics the shared one, padded 14px instead of the spacing variable.
- **UI-14 One control per intent.** Prefer one visible control per intent, variants as its options, and none where existing taps, drags or keys already do it on every device. Yes: `Export ▾` holding CSV and PDF. No: `Resume` and `Open` side by side, both reopening the same document.
- **UI-15 Every enabled control works.** Give every act an item or overlay supports, close and remove included, a working control in its view; remove controls and pages that do nothing. Yes: A photo viewer with its own Delete, and a × that closes it on one click. No: A `Theme` menu item that does nothing when clicked.
- **UI-16 Confirm only what can't be undone.** Ask once before a permanent delete or discarding unsaved work; anything an Undo can bring back runs at once, without asking. Yes: Empty trash → "Delete 12 items forever?" `Cancel` `Delete`. No: "Remove this task?" on a list where Undo restores it.
- **UI-17 Looking never changes data.** Change data only on a control press: opening or viewing never adds to a list, marks done, starts a session or timer, or opts in. Yes: Opening a recipe shows Save; it joins the saved list only when Save is pressed. No: Opening a product page adds it to the cart.
- **UI-18 Every wait shows at once.** Answer every input without perceptible lag; while work runs, disable and relabel the pressed button (Saving…) and run a slim bar under the top bar. Yes: `Save` turns to greyed `Saving…` the moment it is pressed. No: Each day switch reloads the whole page.
- **UI-19 Layout fits its container.** Size layouts to their container, stacking columns before they squeeze, never overlapping or truncating; only shelf rows, and last-resort wide tables, scroll sideways. Yes: Closing a side pane widens the main column into the freed space. No: A two-column form squeezed to 150px fields at phone width.
- **UI-20 One owner per gap.** Each box pads itself, equally on opposite sides and matching its children's gap, with section space above headings and at least 4px between neighbors. Yes: A comment form padded 12px on all sides, 12px between the text box and its buttons. No: A form padded 24px on top and 8px at the bottom.
- **UI-21 Default view holds the frequent.** Prefer showing only what most visits use; put rare settings, details and legal terms behind More or the choice needing them; make optional setup skippable. Yes: A shop owner's home shows today's orders with Ship; tax settings live under Settings. No: Storage used printed under every uploaded file instead of on the account page.
- **UI-22 Theme-safe color and contrast.** Keep text at 4.5:1 and page, panel and callout tones distinct in every theme, saturated color only on state, actions and selection, at full strength. Yes: A tip callout one tone darker than the page in both themes. No: A callout box at #f7f7f7 on a #fafafa page.
- **UI-23 Primary right, others to its left.** Put the primary at the right end, Cancel beside it, other secondaries further left, and leave-or-destroy actions like Discard draft at the far left. Yes: `Discard draft` … `Cancel` `Save`. No: `Save` at the left of a form, `Cancel` at the right.
- **UI-24 Feature parity across devices.** Ship each feature and fix to phone and desktop through one shared feature layer under device-tailored layouts; only keyboard-bound tasks like coding may be desktop-only. Yes: Meeting notes open, edit and delete on the phone, in a phone layout. No: A separate phone page, rebuilt from scratch, that has no Edit.
- **UI-25 Compact by default.** Prefer compact spacing in tools, about 12px between sections and 6px within a row, from shared spacing variables; showcase pages may run roomier. Yes: Sections 12px apart on an admin dashboard. No: A 24px gap between a list and its own heading in a tool.

## Open the topic files before UI work

They live in the `ui-style` skill (`~/.claude/skills/ui-style/`, `~/.codex/skills/ui-style/`). Open each one whose trigger matches before building, not after:

- `core.md`: building or changing any app with more than one screen.
- `components.md`: building or changing a component: forms, lists, tables, dialogs, menus, pickers, editors, media.
- `touch.md`: anything that runs on a phone or tablet, or takes touch input.
- `desktop.md`: anything used on a desktop or laptop screen.
- `assistant.md`: building a chat or AI-assistant interface.
- `personal-tools.md`: a tool only Michael uses, or a mock or review page for him (never a client product or KeepTheCall).
- `process.md`: planning, mocking, reviewing or reporting on UI work with Michael.

Before calling UI work done, run the `ui-review` skill.
